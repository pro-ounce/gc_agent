Skills & Workflows

The agent's guided capabilities come in two shapes — a Skill does one reusable thing; a Workflow strings skills into an end-to-end process and can invoke a skill mid-flow. Both are authored from one declarative pattern. This guide covers the model, the template, the design system, and a live builder.

00 Skills & Workflows

Two building blocks, one authoring pattern. A skill does one thing; a workflow composes skills into an end-to-end process and can branch into another skill mid-flow. Both are declared the same way (the template in the sections below).

Skill — one operation

A single, reusable thing the agent performs end-to-end and self-contained — collect a few fields, confirm, run one tool. Reused across workflows.

Create applicationCreate menuCreate privilegeGrant access

Workflow — end-to-end

A process made of several skills. A step can invoke a skill inline, then return and continue — so one run does the whole job.

Create roleOnboard user
Composition — "Create role" invokes the "Create menu" skill
Create role workflow runs application name admin? menu needs one? → Create menu skill → back → confirm & run

In the widget, the role's menu step offers Pick an existing menu or Create a new menu first — the latter runs the Create menu skill inline, then returns to finish the role. That inline branch is what makes "Create role" a workflow rather than a plain skill.

01 Anatomy

A workflow is one entry in the _ENTITY_CREATE registry, keyed by entity name. Four parts: a human label, the tool run on confirm, the ordered fields, and the fixed defaults set without asking.

_ENTITY_CREATE["role"]
"role": {
  "label": "application role",        # shown in prompts, rail title, cards
  "tool":  "addApplicationRole_post", # MCP tool called at confirm
  "fields": (
    EField("applicationId", "Which **application** is this role for?", kind="app_picker"),
    EField("roleName", "What's the role's **display name**?", maxlen=80, unique="role_name"),
    EField("role", "", auto_from="roleName", is_code=True, maxlen=30, unique="role_code"),
    EField("roleDescription", "A one-line **description**?", maxlen=1000),
    EField("isAdmin", "Is this an **admin** role?", kind="yesno"),
    EField("menuId", "Which **menu** should be mapped to this role?", kind="menu_picker"),
  ),
  "defaults": {"enabled": "Y", "isChatbot": "N"}, # set at finalize, never prompted
}

That is the whole definition — start_entity_create → _entity_create → _efield_step → _entity_finalize read the spec and drive prompting, pickers, validation, uniqueness, the rail, break-out, confirm, the tool call, and the collapsed card.

02 Field types kind=

A field's kind decides what the widget renders. The picker kinds are selectable (violet) — see the next section for how that differs from reference and boolean.

03 Option states — selectable vs reference vs boolean

The single thing to get right. Options are color-coded by role, not by field. A role picker is selectable (violet); the existing role names shown for a unique field are reference-only (amber) — you don't pick them, you avoid them; a yes/no is neither.

04 Field modifiers

On top of kind, each EField takes modifiers that encode the column's real constraints — length, code normalization, uniqueness, and values the engine fills in.

!
Field lists and lengths are verified against the backend entity contracts — the NOT-NULL and unique columns — before shipping. Get them from the tool's schema, not by guessing.

05 Lifecycle

One intent starts the run; each field is one turn; a confirm gates the single side-effect. Nothing is written until the user confirms.

↔
Break-out guard. A real question mid-flow ("what is a menu?") is answered as free-form by _should_break_out without derailing the flow — it resumes, it is not cancelled.
